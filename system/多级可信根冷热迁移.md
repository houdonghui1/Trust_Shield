# 多级可信根冷热迁移问题探讨

> 基于项目《面向异构TEE集群的多级可信根系统》（Trust_Shield）的迁移技术前瞻研究
>
> 涉及主题：固件更新 · 虚拟机/vTPM 可信迁移 · 密钥安全传输

---

## 一、引言：为什么是多级可信根要有迁移能力

### 1.1 研究背景

本项目 README 中"面向异构TEE集群的远程协议与密钥管理的关键技术探索"研究内容第 3 条明确提出：

> **"探索密钥分发协议，以及可信根冷迁移、热迁移关键技术。"**

当前原型系统已完整实现"安全启动 → 逐级度量授权 → 证书链签发 → 远程证明"的信任闭环，但**所有信任关系均锚定在"静态"假设之上**：固件不变、设备不动、密钥不出域。一旦引入以下现实需求，静态假设即被打破：

| 现实需求 | 打破的静态假设 | 对应迁移问题 |
|---------|--------------|-------------|
| 固件漏洞修复、功能升级 | 固件度量基准值固定 | 固件更新（固件的安全"替换"） |
| 虚拟机负载调度、故障切换 | vTPM 状态绑定单一物理平台 | VM/vTPM 冷热迁移 |
| 设备更换、集群扩容 | 密钥与物理芯片强绑定 | 密钥传输与重封装 |
| 密钥轮换、证书到期 | 密钥一次性生成、终身使用 | 密钥分发与更新 |

**核心矛盾**：可信计算要求"信任链完整、度量基准稳定、私钥不出安全域"；而迁移要求"状态可导出、数据可搬运、身份可延续"。两者天然冲突，需要精心设计协议在矛盾中取得平衡。

### 1.2 冷迁移与热迁移的概念界定

借用虚拟化领域成熟概念并结合可信根场景重新定义：

```
┌─────────────────────────────────────────────────────────────────────┐
│                     可信根"冷/热"迁移概念图谱                          │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│   冷迁移（Cold Migration）              热迁移（Hot/Live Migration）  │
│   ┌──────────────────────┐             ┌──────────────────────┐     │
│   │ · 服务/设备停机        │             │ · 服务/设备不停机     │     │
│   │ · 状态静态导出         │   ─────▶    │ · 状态迭代同步        │     │
│   │ · 一次性完整搬运       │             │ · 短暂停顿切换        │     │
│   │ · 目标端重新验证       │             │ · 迁移中保持响应      │     │
│   └──────────────────────┘             └──────────────────────┘     │
│        │                                      │                     │
│        ▼                                      ▼                     │
│   典型场景：                            典型场景：                    │
│   · 固件离线更新（重新上电度量）          · VM 在线迁移（vMotion类）   │
│   · vTPM 状态停机备份/恢复              · vTPM 状态在线同步          │
│   · 设备更换时的密钥迁移                · 密钥在线轮换               │
│   · SD 卡固件重刷                       · 无损固件更新(Hitless)     │
│                                                                     │
│   共同安全前提：迁移过程本身必须纳入信任链（授权、加密、防篡改/回滚/克隆）│
└─────────────────────────────────────────────────────────────────────┘
```

- **冷迁移**：迁移对象处于停机/静态状态，整体导出→搬运→导入→重新验证启动。实现简单、安全窗口可控，但服务中断。
- **热迁移**：迁移对象持续运行，状态分批迭代同步，最后短暂停顿完成切换。业务连续性好，但协议复杂、安全攻击面大（迁移流量可被劫持）。

### 2.2 现有可复用的"准迁移"资产

虽无显式迁移实现，但原型系统中已有若干机制构成迁移协议的基础设施：

| 现有资产 | 位置 | 对迁移的价值 |
|---------|------|-------------|
| UART 32B 分块+ACK 协议 | 二级↔三级（丢包率 0） | 任意大文件（固件包/TPM状态/密钥块）可靠传输的现成信道 |
| 度量-授权控制流（0x5a/0x6a/0x7a/0x8a 信号体系） | `attestation_smoketest.c` | 迁移授权信号可直接扩展（如 0xAa=迁移请求） |
| 逐级证书签发链 | CA→三级→二级→一级 | 迁移后新平台身份的再注册通道 |
| AES-256-ECB 预共享密钥加密 | CA→三级 AK 证书下发 | 迁移数据机密性的雏形（需升级，见第五章） |
| SWTPM 控制通道（unixio socket） | `start.sh` | swtpm 原生支持状态导出/导入的接口基础 |
| ioctl 命令体系（GENERATE/SAVE/GET/SIGN/VERIFY CTX） | `caliptra_io.c` | 密钥/证书安全操作的统一入口，可扩展迁移命令 |
| 一级 ERROR 态保留运行态设计 | 一级固件设计 | 固件更新失败回滚的状态机基础 |

### 2.3 迁移的三大安全约束（威胁模型）

任何迁移方案必须先明确"不可破坏的红线"：

**红线 1：度量基准一致性**

```
三级固件中: g_2nd_rom_expected_val[32]  ← 二级ROM基准(当前硬编码)
一级固件中: FMC_expected_digest / SOC_expected_digest ← 一级固件基准
```

固件更新后度量值必然改变 → 基准必须**同步受控更新**，否则系统永久拒绝启动；若基准可被随意篡改 → 恶意固件可绕过度量。**基准更新必须由上级可信根签名授权**。

**红线 2：私钥不出安全域**

DICE 链中 UDS→CDI→各级密钥均在 Caliptra/OpenTitan 内部派生，"签名后清除前级私钥"是核心安全设计。任何密钥迁移方案不得将**根密钥（UDS/IDevID）**导出；可迁移的只能是**受策略约束的派生密钥**（业界对应 TPM2_Duplicate 的 newParent 机制）。

**红线 3：身份不可克隆**

EK/AK 与物理芯片绑定（PUF/OTP）。若 vTPM 状态直接复制到两个平台 → 同一身份两处存活 → 远程证明失效。**迁移必须保证"唯一性承诺"：源端销毁与目标端激活是原子操作**（两阶段提交）。

**威胁清单**：

| 攻击 | 目标 | 对策方向 |
|------|------|---------|
| 迁移流量劫持/篡改 | 注入恶意固件/TPM状态 | 迁移数据签名+加密信道 |
| 回滚攻击 | 恢复含漏洞旧固件绕过补丁 | 版本单调计数器/防回滚熔丝 |
| 克隆攻击 | 复制 vTPM 身份双处运行 | 两阶段提交+源端销毁证明 |
| 重放攻击 | 重放旧迁移会话 | Nonce+时间戳+会话绑定 |
| 中间人 | 窃取传输中的密钥材料 | 目标平台公钥封装(ECDH) |

## 三、场景一：各级可信根固件更新——固件的"冷迁移"

### 3.1 概念：固件更新即受控的固件替换

固件更新本质上是"新固件从可信构建环境 → 设备存储区 → 激活运行"的**三段式冷迁移**，每一段都必须有密码学保护：

```
┌─────────────────────────────────────────────────────────────────────┐
│                     固件更新三段式冷迁移流水线                          │
│                                                                     │
│  [段1: 构建侧]        [段2: 传输/存储侧]        [段3: 设备侧激活]     │
│  ┌──────────┐  签名   ┌──────────────┐  验签  ┌────────────────┐    │
│  │ 源码+构建 │ ─────▶ │ 暂存区(Staging│ ─────▶ │ A/B分区切换+    │    │
│  │ 产出固件  │        │ Area,非激活区)│        │ 度量基准更新+    │    │
│  │          │        │              │        │ 上级重新度量授权 │    │
│  └──────────┘        └──────────────┘        └────────────────┘    │
│   ▲ 完整性锚点:         ▲ 防掉电/篡改:            ▲ 防回滚/防降级:    │
│   开发者签名私钥        分块CRC+ACK             版本号单调递增        │
└─────────────────────────────────────────────────────────────────────┘
```

### 3.2 业界参考机制（网络调研）

#### 3.2.1 A/B 分区（双 Bank）机制

Caliptra MCU 固件更新文档给出了业界标准的 A/B 分区方案（同样适用于 OpenTitan owner 固件更新、MCU OTA）：

```
┌──────────────────────── Flash 布局 ────────────────────────────┐
│  ┌──────────── Partition A (Active) ────────────┐              │
│  │ Flash header | 校验和 | Image Info(FMC+RT/    │   当前运行   │
│  │ Manifest/MCU RT/SoC Image 1..N) | 固件实体     │              │
│  └───────────────────────────────────────────────┘              │
│  ┌──────────── Partition B (Inactive) ──────────┐              │
│  │ 同构布局 —— 更新写入目标区                     │   更新暂存   │
│  └───────────────────────────────────────────────┘              │
└─────────────────────────────────────────────────────────────────┘

分区表（Flash 保留区）:
┌──────────────────┬──────┬───────────────────────────────────┐
│ 字段              │ 大小 │ 说明                               │
├──────────────────┼──────┼───────────────────────────────────┤
│ Active Partition │ 1B   │ 当前激活分区 A/B                    │
│ Partition A Status│ 1B  │ 状态[7:4]=尝试计数 [3:0]=          │
│                  │      │ 0无效/1有效/2启动失败/3启动成功      │
│ Partition B Status│ 1B  │ 同上                               │
│ Rollback Flag    │ 1B   │ 是否允许回退另一分区                │
│ CheckSum         │ 4B   │ 分区表自身完整性                    │
└──────────────────┴──────┴───────────────────────────────────┘
```

**关键性质**：更新期间系统始终运行在 Active 分区；新固件写满 Inactive 分区并标记 VALID；激活时切换指针；新分区启动失败自动回退（Boot Attempt Count 限制重试次数，防无限循环降级）。

#### 3.2.2 PLDM-T5 固件更新协议（DMTF DSP0267）

Caliptra MCU 采用 PLDM for Firmware Update (Type 5) 作为传输编排协议，流程：

```
QueryDeviceIdentifiers → GetFirmwareParameters → RequestUpdate
→ PassComponent(逐组件) → UpdateComponent
→ RequestFirmwareData(分块循环) → VerifyComponent
→ ApplyComponent → ActivateFirmware
```

验证阶段的三类校验分别由不同信任锚执行：
- Caliptra FW Bundle → `FIRMWARE_VERIFY` mailbox 命令（Caliptra ROM 验签）
- SoC Manifest → `VERIFY_MANIFEST` mailbox 命令（Caliptra 验证清单）
- MCU RT / SoC Image → MCU 计算 Hash 与已验证 Manifest 中的摘要比对

#### 3.2.3 Hitless Update（无损更新）

Caliptra 2.1 支持 MCU 固件热更新而不复位整个 SoC：`RESET_REASON=FW_HITLESS_UPD_RESET`，MCU SRAM 更新区重映射+定向复位。这是"固件热迁移"的雏形——**对业务处理器隐藏可信根自身的更新**。

#### 3.2.4 防回滚（Anti-Rollback）

Caliptra 通过 Owner 安全状态与防回滚熔丝（fuses）支持强防回滚：新固件版本号写入一次性熔丝组后，旧版本固件永久无法通过验证。弱方案（计数器在可重写存储中）可配合签名版本号实现"软防回滚"。

### 3.3 本项目各级固件更新方案设计

#### 3.3.1 一级可信根固件更新（当前最成熟）

现状：FMC 固件（2048 扇区）、RT 固件（4096 扇区）、SOC_FW（6144 扇区）固定布局于 SD 卡，`dd` 重写即完成"更新"，上级重新度量授权。

```
┌──────────────── 一级固件更新流程（建议方案）─────────────────────┐
│                                                               │
│ ① 构建侧: 新FMC/RT/SOC_FW + 版本号v2 → 开发者签名               │
│ ② 分发: 三级可信根下发固件包(UART 32B分块+ACK, 复用现有协议)     │
│         或人工SD卡更换(冷迁移, 现状)                            │
│ ③ 二级中转: 二级校验签名 → 写入一级SD卡新分区(FMC@B区)           │
│ ④ 度量基准更新: 二级下发"基准更新令牌"(见3.4)                   │
│ ⑤ 重启授权: 一级重新上电 → Caliptra度量新固件                   │
│         → PCR(新) 上报二级 → 二级比对"基准更新令牌"内含期望值    │
│         → 授权启动 / 失败回退旧分区                             │
└───────────────────────────────────────────────────────────────┘
```

改造点：SD 卡从"固定偏移单分区"改为 A/B 双分区（FMC_A/FMC_B 等），ROM 固件读分区表选择启动目标——参考 Caliptra MCU 分区表格式即可，一级 Caliptra ROM 已具备 ECDSA 验签与 SHA512 度量能力，仅需增加分区表解析逻辑。

```

#### 3.3.3 三级可信根固件更新（OpenTitan eFlash）

三级自身固件（ROM_EXT 验签的管理固件）更新依托 OpenTitan 原生能力：
- **owner firmware update**：OpenTitan 官方支持 owner 阶段固件的 A/B slot 更新（boot ROM 校验 slot 签名后跳转）；
- 生命周期约束：`PROD` 状态下 ROM 本体不可更新（这是设计使然——ROM 是信任锚）；可更新的是 ROM_EXT 及其后的管理固件；
- 更新包可由 Privacy CA 通道下发（复用 `AK_CERT:` 前缀 + AES 加密帧格式），或经 SAM3X 扩展板 SPI 直接烧写 eFlash（现场维护模式，受 lifecycle `DEV` 状态保护）。

#### 3.3.4 固件更新时序整合（time6 阶段建议）

在现有 time1~time5 时序后扩展 **time6（维护窗口）**：

| 步骤 | 发起者 | 动作 | 安全关键点 |
|------|--------|------|-----------|
| 1 | 运维/CA | 向三级提交"更新计划"（目标层级、版本、签名固件包） | 计划需三级 AK 私钥签名确认，防伪造下发 |
| 2 | 三级 | 校验固件包签名+版本号 ≥ 当前版本（防回滚） | 单调版本比对 |
| 3 | 三级 | 生成"基准更新令牌"（新度量期望值+有效期+目标ID，三级签名） | 令牌短期有效，一次性 |
| 4 | 三级→二级（→一级） | 分块下发固件至 staging + 令牌 | 传输加密（第五章会话密钥） |
| 5 | 下级 | 写入非激活分区，标记 VALID，请求重新度量 | 不触碰激活分区 |
| 6 | 上级 | 度量 staging 固件，比对令牌内新基准 | 比对失败→拒绝切换 |
| 7 | 下级 | 切换分区表 Active 指针，重启走新固件 | 失败自回退（尝试计数） |
| 8 | 各级 | 上报新 PCR → 逐级重新授权+重签设备证书（若 DICE 层级变化） | 证书与固件版本绑定 |

### 3.4 度量基准管理机制（固件更新的信任核心）

基准是"度量的度量"，其管理方案分三级强度：

| 方案 | 存储 | 更新方式 | 安全强度 | 适用 |
|------|------|---------|---------|------|
| A. 硬编码基准（现状） | 固件常量 | 重新编译烧写上级固件 | 最高但不可运营 | 原型验证 |
| B. 签名基准包 | 上级 NV 存储 | 上级私钥签名的{目标ID,版本,期望值,有效期} | 中，可在线更新 | **推荐近期采用** |
| C. 单调计数器+基准链 | OTP 熔丝/单调计数器 | 版本号烧丝，基准值链式哈希 | 高，抗回滚 | 量产 |

方案 B 的令牌格式建议：

```
BASELINE_TOKEN ::= {
  target_id     : 设备ID/层级标识        // 防跨设备重放
  fw_component  : FMC | RT | SOC_FW | caliptraROM
  new_version   : uint32 单调递增        // 防回滚
  expected_hash : SHA256/SHA512(新固件)   // 新度量期望值
  not_before / not_after : 有效时间窗口    // 防延迟重放
  issuer_sig    : 上级可信根私钥签名      // 完整性+来源认证
}
```

## 四、场景二：二级系统虚拟机迁移与 vTPM 的移动

### 4.1 现状分析：vTPM 的"易碎"状态

当前二级系统的 vTPM 部署（`Second_rot_sw/trust_root_2nd_1014/test/start.sh`）：

```
┌────────────── 当前二级 vTPM 架构 ──────────────────┐
│  QEMU VM (Ubuntu Minimal, ~140MB)                  │
│    └─ /dev/tpm0 (tpm2_getrandom 验证可用)          │
│         │ TPM 命令                                  │
│  ═══════╪════════════════════════════════════      │
│         ▼                                          │
│  swtpm socket --tpm2                               │
│    ├─ 命令通道: /tmp/mytpm1/swtpm-sock (unixio)     │
│    ├─ 控制通道: swtpm-ctrl (★ 迁移能力所在)          │
│    └─ 状态存储: /tmp/mytpm1/ (★ 非持久化!)          │
│         │ ioctl(CALIP_TRNG_IOCTL_GEN)              │
│  ═══════╪════════════════════════════════════      │
│         ▼                                          │
│  内核驱动 caliptra_dev.ko                           │
│    └─ PL端 Caliptra TRNG (硬件熵源卸载)             │
└────────────────────────────────────────────────────┘
```

三个关键问题：
1. **状态非持久化**：`rm -rf /tmp/mytpm1` 后 `swtpm_setup --createek` 重建——每次重启 vTPM 身份"归零"，EK/密钥/PCR 全部重置；
2. **无迁移接口**：未利用 swtpm 控制通道的迁移能力；
3. **硬件卸载耦合**：vTPM 熵源绑定本平台 PL 端 Caliptra——迁移到无 Caliptra 的平台，安全属性降级为纯软件 swtpm。

### 4.2 业界参考机制（网络调研）

#### 4.2.1 QEMU/swtpm 官方迁移机制

QEMU TPM 文档明确了 emulator 后端的三种迁移能力与约束：

| 迁移类型 | TPM 状态传输方式 | 状态目录要求 |
|---------|----------------|-------------|
| save/restore（冷迁移基础） | `migrate "exec:cat > vm.bin"` 整体落盘 | 恢复时相同参数（含 `--tpm2`） |
| 网络迁移（热迁移） | swtpm 控制通道协商，状态随 VM 迁移流传输 | 两端目录路径一致 |
| 快照 | 迁移到 QoW2/QED 存储 | 相同目录 |

**关键安全特性**：`swtpm --migration-key` 支持迁移状态加密，目标端用相同密钥解密——防止迁移流量中 TPM 状态（含密钥材料）被窃听。

**硬性限制**：硬件 TPM passthrough 模式**禁用迁移**（"none of the state of a hardware TPM can be migrated"）——这正是本项目"二级平台 Caliptra 卸载"必须坚持 vTPM 软件态可序列化的原因：**卸载的是密码运算与熵源，而不是状态**。

#### 4.2.2 KVM vTPM 动态迁移方案（学术方案）

山东大学学报《一种基于KVM的vTPM虚拟机动态迁移方案》给出典型架构：源端与目的端建立传输通道，虚拟机内存数据迭代传输，满足停机条件后短暂停机完成最后一次内存与虚拟硬件状态（含 vTPM 状态）同步。该方案与本项目的启示：**vTPM 状态应作为"虚拟硬件状态"纳入统一迁移流**，而非独立旁路搬运。

#### 4.2.3 vSphere 的启示：vTPM 迁移 = 状态迁移 + 密钥体系迁移

VMware vSphere 中启用 vTPM 强制绑定 VM Encryption（虚拟机盘与状态加密），宿主加密密钥由 KMS 托管、受主机签名/加密证书保护。迁移时：
- vTPM 状态文件（.nvram 类）随 VM 盘一起被加密搬运；
- 解密能力（KMS 密钥授权）必须在目标主机就绪；
- **本质是"密钥管理体系先行，状态随后"**——目标平台的可信根必须先获得解密授权，vTPM 状态才能落地。

### 4.3 多级可信根场景下的 vTPM 迁移方案

#### 4.3.1 前置改造：vTPM 状态持久化与外置封装

第一步（无迁移也受益）：状态从 `/tmp` 迁到受管存储并绑定硬件根：

```
┌──────── vTPM 状态持久化封装（改造后）────────────────┐
│                                                    │
│  swtpm --tpmstate dir=/var/lib/vtpm/<vm-id>/       │
│                                                    │
│  状态文件: tpmt_state.md                            │
│      │ 用"平台封装密钥 PEK"加密                      │
│      ▼                                             │
│  PEK = KDF( PL端Caliptra根密钥, vm-id )             │
│        ↑ 由二级 Caliptra DataVault 派生,不出PL      │
│                                                    │
│  效果: 状态文件离开本平台即密文,                     │
│        只有持有同源 Caliptra(或其授权)的平台可解     │
└────────────────────────────────────────────────────┘
```

`PEK`（Platform Encapsulation Key）由 PL 端 Caliptra 从平台根密钥经 KDF 派生，通过新增 ioctl（如 `CALIP_TPM_SEAL/UNSEAL`）供 swtpm 调用。这与 TPM2_Duplicate 的哲学一致：**封装密钥决定"谁能解开"**。

#### 4.3.2 vTPM 冷迁移协议（同集群二级平台间）

```
┌─────────────────── vTPM 冷迁移六步协议 ────────────────────────┐
│                                                               │
│   三级可信根(集群管理者)      源二级平台A         目标二级平台B    │
│   ┌──────────┐            ┌──────────┐        ┌──────────┐     │
│   │ 迁移授权M │ ①迁移请求   │ VM停机    │        │ 预置Caliptra│    │
│   │          │ ◀───────── │  SWTPM暂停│        │ 预置驱动    │    │
│   │ 校验B平台 │            │          │        │          │     │
│   │ 证书/PCR  │ ②迁移令牌MT │          │        │          │     │
│   │          │ ─────────▶ │          │        │          │     │
│   └──────────┘            │ ③导出状态 │        │          │     │
│        │                  │  EK/密钥树 │       │          │     │
│        │  B在CA/三级处完成 │ PCR bank   │       │          │     │
│        │  平台注册(设备证书)│ NVRAM清单  │        │          │     │
│        │                  │ ④PEK解封   │        │          │     │
│        │                  │  →MT中B的  │        │          │     │
│        │                  │  公钥重封装 │       │          │     │
│        │                  │ ⑤加密传输  │ ─────▶ │ ⑥校验MT  │     │
│        │                  │  (状态+证明)│       │  解封导入  │     │
│        │                  │  源端状态  │        │  启动VM    │     │
│        │                  │  安全擦除  │        │          │     │
│        │ ◀───────────────── 迁移完成上报 ─────── │          │     │
│        │ 审计: A销毁证明 + B激活证明                 │     │
│        └──────────────────────────────────────────────┘     │
└───────────────────────────────────────────────────────────────┘

迁移令牌 MT ::= {
  vm_id, 源平台ID, 目标平台ID,          // 绑定迁移双方
  目标平台PEK公钥,                      // 状态重封装的newParent
  一次性nonce, 有效期,                  // 防重放
  三级私钥签名                           // 授权证明
}
```

**与 TPM 2.0 标准的关系**：④"重封装"直接对应 `TPM2_Duplicate`——将 vTPM 内受旧父密钥（源平台PEK）保护的密钥树，在源端安全边界内改封装到新父密钥（目标平台PEK公钥）下；密钥材料全程以封装态（duplicated blob）存在，**明文私钥从不出现**。

#### 4.3.3 vTPM 热迁移方案（研究级）

在冷迁移协议上叠加"迭代同步"：

```
阶段1 预拷贝(pre-copy):  VM运行中, vTPM状态快照(NVRAM增量+PCR快照)
                        随VM内存页迭代传输; 脏页/脏TPM状态反复重传
阶段2 停机拷贝(stop-and-copy): 短暂停VM → 最后一轮内存+TPM状态
                        + 迁移令牌核验 → 目标端导入
阶段3 激活: 目标端 swtpm 加载状态 → 恢复VM运行 → 源端擦除

安全增强(相对通用方案):
  · 每轮迭代块附加HMAC(会话密钥), 防传输篡改
  · 会话密钥 = ECDH(源PEK, 目标PEK) 派生, 三级令牌背书
  · stop-and-copy 阶段状态哈希锚入迁移完成上报, 三级审计比对
```

**难点提示**：TPM 命令窗口内的状态一致性（迁移中 VM 发起的 TPM 命令需在切换点原子归属）；建议 swtpm 侧增加"迁移态暂停命令队列"，在 stop-and-copy 前排空。

#### 4.3.4 硬件卸载属性的迁移处理

vTPM 迁到目标平台后，其熵源/TRNG 卸载路径需要重新建立：

| 卸载属性 | 冷/热迁移后处理 |
|---------|----------------|
| TRNG 熵源 | 目标平台 PL 端 Caliptra 存在 → `mainloop_patch` 同款补丁自动生效；不存在 → 降级为宿主 `/dev/hwrng`，并在 vTPM 状态元数据中记录"熵源等级"，远程证明 Quote 中体现（可信等级分级） |
| PCR 存储 | vTPM PCR 属软件状态，随状态文件迁移；若曾启用"PCR 硬件锚定"（扩展进 PL Caliptra PCR），需在迁移协议 ⑥ 步做源端导出→目标端重扩展 |
| 签名加速 | 无状态性，目标平台自动可用 |

**设计原则**：**状态可迁移，能力（capability）不可迁移——能力只能重新申请**。迁移后 vTPM 的"硬件背书等级"由目标平台当前硬件拓扑决定，并通过证明协议如实披露，由验证方决定是否接受降级。

## 五、场景三：密钥的传输

### 5.1 现有密钥体系与传输现状

```
┌─────────────────── 现有密钥/证书传输全景 ───────────────────────┐
│                                                               │
│  密钥层级(各级内部, 均不出安全域):                              │
│  三级: PUF→UDS→(OpenTitan密钥管理器)→EK/AK(ML-DSA-87)           │
│  二级: Caliptra KeyVault→P-384设备密钥(签发一级证书用)           │
│  一级: UDS→CDI→IDevID→LDevID→Alias_FMC→Alias_RT (DICE链)        │
│                                                               │
│  实际发生的传输(均为证书/公钥/密文, 无明文私钥):                  │
│  ① 三级→CA:    EK证书+AK公钥+ML-DSA公钥     (UART, 白名单校验)   │
│  ② CA→三级:    AK证书                       (AES-256-ECB,      │
│                                              预共享密钥0x00..1f)│
│  ③ 二级↔三级:  TBS/设备证书(32B分块+ACK)    (明文DER传输)        │
│  ④ 一级↔二级:  CSR/PCR/证书                 (HEX ASCII, 0xAA55 │
│                                              同步头)            │
│  ⑤ 二级→vTPM:  TRNG熵(硬件卸载)             (ioctl→mailbox)    │
└───────────────────────────────────────────────────────────────┘
```

**现状评估**：
- ✔ 方向正确：私钥从未出域，传输的都是证书/公钥/密文；
- ✘ ②的 AES-256-**ECB** + **硬编码预共享密钥**仅适用于原型（ECB 相同明文块产生相同密文，无前向安全；密钥泄露即全线失守）；
- ✘ ③④明文证书传输依赖信道物理隔离假设，集群化后不成立。

### 5.2 业界参考机制（网络调研）

#### 5.2.1 TPM 2.0 Duplication 体系（私钥迁移的标准答案）

TPM 2.0 规范为"密钥迁移"设计了完整命令族，核心思想是**封装（encapsulation）而非暴露**：

```
TPM2_Duplicate( privKey, newParentPub, policy )
   → duplication blob (用 newParent 公钥封装的私钥密文)

  源TPM                            目标TPM
  ┌──────────────┐                ┌──────────────┐
  │ 老父密钥保护下 │  TPM2_Duplicate │              │
  │ 的私钥        │ ─────────────▶ │ TPM2_Import  │
  │              │  (newParent    │ 在新父密钥下  │
  │              │   公钥封装)     │ 重封装私钥    │
  └──────────────┘                └──────────────┘
  · 私钥明文只在两端 TPM 内部出现
  · newParent 由 Policy 控制(可要求"仅特定PCR状态/特定平台可导入")
  · 配套 TPM2_Key / Duplicate policy 语法可表达"允许迁移到谁"
```

学术界在此之上发展了 MDKMP（Make Duplication Key Migration Protocol）等协议：在 SRK 下设立专用迁移密钥 MAK 并申请迁移认证证书，实现密钥迁移的双端可审计。

#### 5.2.2 密钥封装与策略解锁

Linux 生态的 Clevis/TPM2 全盘解锁实践展示了"密钥分发"的另一种形态：**分发的是被策略封装的密钥，而非密钥本身**——TPM 按 PCR 策略决定是否解封。迁移到本项目语境：上级向下级分发会话密钥时，可绑定"下级 PCR 处于合规态"作为解封条件，**密钥与平台状态联动**。

#### 5.2.3 vSphere/微软的密钥托管体系

vSphere vTPM 强制 VM Encryption、Hyper-V vTPM 用主机双证书（加密+签名）保护 VM 状态——共同点：**密钥传输永远发生在"密钥管理系统（KMS/CA）与可信根"之间，用户态永远只见密文**。三级可信根天然适合充当本集群的 KMS 角色。

### 5.3 本项目密钥传输方案设计

#### 5.3.1 分层密钥传输模型

按"什么密钥、允许什么移动方向"建立矩阵：

| 密钥类别 | 可否出域 | 允许的传输形态 | 说明 |
|---------|---------|---------------|------|
| 根密钥 UDS/PUF 种子 | ✘ 永不 | 无 | 信任锚，物理内生 |
| IDevID 私钥 | ✘ 永不 | 无 | DICE 首环，签后即清 |
| LDevID/Alias 私钥 | ✘ 永不 | 无（随固件版本重派生） | CDI=HMAC(前级, 固件hash)，固件更新天然轮换 |
| EK 私钥 | ✘（物理TPM）/ ✔受控（vTPM） | vTPM 场景随状态加密迁移 | 需唯一性承诺（第四章） |
| AK/设备私钥 | ✘ 常规/ ✔ 特批 | Duplicate 封装迁移 | 平台退役、设备更换场景 |
| 会话密钥（对称） | ✔ | ECDH 协商派生 | 每次会话新生，前向安全 |
| 证书/公钥 | ✔ | 签名保护的明文分发 | 现有体系已具备 |

#### 5.3.2 升级一：预共享密钥 → ECDH 会话密钥（替换 AES-ECB）

针对现状②的短板，将 AK 证书下发等对称加密场景升级为**临时密钥协商**：

```
┌────────── 会话密钥协商（三级↔CA / 三级↔二级 通用）──────────┐
│                                                           │

## 七、结论

1. **迁移是信任链从"静态闭环"走向"动态可运营"的必经之路**。当前原型已完成"建链"（启动度量授权）与"证链"（远程证明），迁移补齐的是"续链"能力——固件可换、负载可搬、密钥可流转，而信任链不断裂。

2. **三类迁移共享同一治理模型**：三级可信根作为迁移控制平面，以"签名令牌 + 单调版本 + 两阶段提交 + 审计归档"四要素统摄固件更新、vTPM 迁移与密钥传输；数据平面复用已验证的 UART 32B 分块协议并叠加认证加密。

3. **固件更新优先落地**：一级 SD 卡 A/B 分区与三级"签名基准包"机制改造成本最低、收益最直接，且与 Caliptra MCU（PLDM-T5/A-B分区/Hitless Update）业界路线完全同构，可平滑对接上游生态。

4. **vTPM 迁移的关键洞察是"状态可迁移、能力须重申请"**：swtpm 控制通道原生支持状态导出导入，本项目需补的是 PEK 平台封装密钥（Caliptra 派生）与三级迁移令牌两层保护；硬件卸载属性（TRNG/PCR 锚定）在迁移后如实降级披露，由证明协议承载。

5. **密钥传输的红线不变、手段升级**：根密钥与 DICE 私钥永不迁移的边界保持不变；对称场景由 AES-ECB 预共享密钥升级为 ECDH+GCM 临时会话；设备更换场景引入 TPM2_Duplicate 同构的封装迁移 + 擦除证明；长期由三级可信根演进为集群 KDS，并预留 ML-KEM 抗量子协商通道。

6. **与远程证明的闭环**：所有迁移事件（固件版本变化、vTPM 落户变化、密钥继承关系）应记入 Quote 可披露的元数据，使验证方在挑战-响应时能感知迁移历史——**迁移不是信任链的例外，而是被度量的一部分**。
